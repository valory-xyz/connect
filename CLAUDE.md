# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Pearl BYOA agent server: a localhost FastAPI binary (`127.0.0.1:8716`) that the Pearl middleware runs so a Claude Code or Codex session can act as an Olas Pearl agent — signing and broadcasting on-chain actions as the service safe — without ever touching key material. The session names actions (via MCP tools or HTTP endpoints); this server signs and broadcasts them through a single guarded choke point.

Note: `connect/assets/CLAUDE.md` is a **shipped asset** — the context brief written into the agent's workspace (STORE_PATH) at runtime, as `CLAUDE.md` and `AGENTS.md`. It is not instructions for this repo.

## Keep docs in sync

CLAUDE.md and README.md must be kept updated with any change in the repo — they must not drift in any commit. If a change alters behavior, commands, architecture, endpoints, guardrail semantics, or dependencies described in either file, update that file in the same commit.

- **100% test coverage** on `connect/`, including the shared agent-runtime modules under `connect/assets/lib/`. Only the bundled skills under `connect/assets/skills/` are omitted: they run in the agent's environment, not the server's, and have their own tests.
- mypy with `--disallow-untyped-defs`; `connect/assets/skills/connect-polymarket/` is excluded (depends on the Polymarket CLOB SDK, which the agent's environment installs; the repo keeps it out of `uv.lock`, and `tox -e unit-tests` layers it on for the skill tests with `uv run --with`, so a plain `uv run pytest` skips them). `connect/assets/lib/` is excluded from the *scan* but sits on `mypy_path` and is still fully checked as an import of the skill scripts — without the exclude mypy resolves it under two module names and halts.
- flake8 includes docstring rules (D) and pytest style (PT); every module/function needs a docstring.
- Copyright headers (Valory AG, Apache 2.0) on every source file — `tox -e fix-copyright` adds them.
- `packages/valory/connections/`, `packages/valory/protocols/`, `packages/open_aea/` are vendored third-party code, excluded from all linters — don't edit or reformat them.
- gitleaks scans the history of every branch, not just the PR's (`fetch-depth: 0`), so a fixture that looks like a secret on any branch fails every PR. Allowlist the exact value in `.gitleaks.toml`, not the file or rule.

## Architecture

The security architecture is the thing to understand first: **every signing path funnels through one gate with no bypass.** MCP tools, HTTP signing endpoints, and the mech request flow all reduce to `Signer.send()` / `Signer.sign_digest()` (`connect/signer.py`), and every request passes the guardrail in `connect/guard.py` before signing — and, for a transaction, the intent gate in `connect/intent.py` after it. Two invariants hold in every mode and no setting lifts them: the safe may not `delegatecall`, and the safe may not call itself. On that floor sit two persistent modes: **unrestricted** (default) and **restricted** (operator opt-in via the UI: only safe `execTransaction` CALLs to whitelisted addresses, gas-refund fields zeroed, no raw digest signing — except single-use allowances the mech flow registers for the safe's ERC-1271 wrap of off-chain request ids it derived locally and for the one capped safe→tracker deposit a 402 top-up would send, and the same native shape for the agent top-up (README, "Agent top-up")). The modes are an operator concept only — agent-facing surfaces (MCP tools, `/wallet`, the workspace brief and skills, guard refusal messages) deliberately never mention that modes exist; `EXPOSE_MODE_TO_AGENT` in `connect/settings.py` is the one switch that turns the agent-visible mode readouts back on. The reasoning is documented at the top of `guard.py`.

Core modules:

- `connect/__main__.py` — entrypoint; decrypts the keystore (`connect/keystore.py`) in memory, provisions the workspace, starts the server.
- `connect/workspace.py` — provisions STORE_PATH (the agent session's cwd) for both harnesses: the MCP entry with a fresh per-run bearer token (`.mcp.json`, `.codex/config.toml`), the brief (`CLAUDE.md`, copied to `AGENTS.md`), and the bundled skills from `connect/assets/skills/` with the shared modules they import from `connect/assets/lib/`, installed as `skills/` and `lib/` under both `.claude/` and `.agents/`. A bundle missing either is a broken bundle: provisioning fails and the server reports itself unhealthy. Codex loads that config only once the operator trusts the folder at Codex's own prompt; Connect never edits the user's Codex config. `codex_cli` has no URL handler, so it opens a terminal running `codex` instead, once `codex` resolves in the login shell (README, "Codex"). It also opens the session, and does so through `harness_env()`, which strips the dynamic-loader variables our PyInstaller packaging leaks (`LD_LIBRARY_PATH`/`DYLD_LIBRARY_PATH` + their `_ORIG` twins, `_PYI_*`) — left in, our bundled OpenSSL shadows the system one and every node-based hook and MCP server in the session fails, the MCP servers silently. See the `LOADER_ENV_VARS` comment.
- `connect/signer.py` — the single signing choke point. Its per-chain Web3 clients sit on `RotatingHTTPProvider` (the `open-aea-ledger-ethereum` plugin), built without a `chain_id` so chainlist.org enrichment stays off — `test_rpc_pool_is_built_without_a_chain_id` in `tests/test_extras.py` carries the reasoning and enforces it. What it buys is retry for the methods web3 does not already cover: a bare `HTTPProvider` retries the 43 in `REQUEST_RETRY_ALLOWLIST`, so the gain is the rest — `eth_feeHistory`, on the EIP-1559 fee path of every send. It buys nothing for writes. `eth_sendRawTransaction` is on web3's allowlist, so the pooled inner provider re-broadcasts before the outer write rule is ever reached (measured: one 503, two sends, on a bare and a rotating provider alike), and a post-send read timeout classifies as `connection` in `CONNECTION_SIGNALS` — so "retried only on clear pre-send failures" is not true of the stack as shipped. The bytes are identical, so a re-broadcast cannot double-spend; what it can do is surface a transaction that landed as failed, via "already known" or "nonce too low". That covers this pool only: mech-client builds its own `EthereumApi`, which always passes a `chain_id`, so the mech flow does reach chainlist. `parse_rpc_urls` means a comma-separated address would rotate here, but `mech.py` and `wallet.py` hand the same string to single-URL consumers — so that form is unsupported until they agree.
- `connect/intent.py` — the intent gate (README, "Intent gate"): `simulate` runs `eth_simulateV1` over the chain's RPC and folds the logs into an `AssetDiff`, `check_intent` applies the rules, `parse_intent` validates what a caller sent, and `Capped` wraps a value-capped token's intent so no position may leave under it (the send surfaces apply it; no request body can). Pure functions over an injected `rpc` and `get_code`; `Signer._send_guarded` calls it after the guard on every send except those marked `SERVER_BUILT` (the mech flow and the agent top-up, the server's own transactions — a private object, so no request body can produce it); its `gate` is required, and that sentinel is the only skip. Calldata that is not hex is the gate's `bad-calldata` (`_calldata_problem`), before any RPC.
- `connect/chain_read.py` — `chain_call`, `get_abi` and `decode_calldata` behind the read-only MCP tools. `get_abi` knows only what Connect ships (`KNOWN_CONTRACTS`: Multicall3, Permit2 and the contracts the bundled skills call, each a `KnownContract` with a named signature tuple and the chain ids it is deployed on, kept in step with the skills' own constants by `tests/test_chain_read.py`, and looked up only on those chains by `known_contract`, which `auth.py` shares; and ERC-20/721/1155 by what a contract answers) and follows the EIP-1967 slot; no block-explorer call. `verified` speaks for the queried address alone: the slot is the contract's own storage, so its target is reported as `implementation_verified`. `decode_calldata` refuses input past `MAX_CALLDATA_BYTES` and a decoded tree past `MAX_DECODED_BYTES` (`decoded arguments too large`): ABI offsets may all point at one blob, so a small input can otherwise decode to many copies of it.
- `connect/guard.py` — the guardrail; one gate for every signing path. `check_transaction` takes `consume=False` so a dry run can ask without spending an allowance (README, "Guardrail").
- `connect/safe.py` — the only place that knows what an `execTransaction` looks like. The agent names an inner call (target, value, calldata); the server wraps it in the safe's `execTransaction` with a threshold-1 pre-validated signature. `SafeExec.decode` is the one decoder of execTransaction bytes, used by the guard's floor and by `Signer._eoa_gate` (an EOA send of `execTransaction` to the configured safe is gated as the safe's call; `pays_refund`, a non-CALL operation, EOA value and the safe's `approveHash` are refused there, after the guard, so they are audited). `calldata_hex` is the one reading of a calldata string every selector check shares — the guard's, `_eoa_gate`'s, these decoders' and `chain_read.decode_calldata`'s — so a `0X` prefix, which a signer reads as the same bytes, cannot hide a selector.
- `connect/settings.py` — tamper-evident settings persisted in STORE_PATH. Security-critical fields (mode, whitelist) are HMAC'd with a key derived from the agent private key; a failed verification resets them to the (unrestricted) defaults — deliberate and audited, see the module docstring for the reasoning. The last-written MAC is also pinned in memory to defeat replay of old settings files. The `harness` preference sits outside the MAC deliberately (it can't move funds).
- `connect/mech.py` — mech marketplace requests via mech-client's `Signer` protocol, so every transaction/digest still passes the choke point. An optional caller-chosen `request_id` makes a request replayable, and an optional `request_context` dict rides along in the request metadata for the tool (README, "Mech requests"). `metadata_extras` builds those extras once so the off-chain digest and mech-client hash the same bytes; `request_stamp` covers the context too, since the same prompt with a different market price is a different question. Both live in `connect/mech_stamp.py`, split out for pylint's line limit.
- `connect/mech_nonces.py` — `NonceAllocator`, Connect's off-chain marketplace nonce allocator, one queue per (chain, safe), persisted in `mech_nonces.json` (README, "One payer per safe: nonces"). `reserve` holds the queue's lock until the mech answers; `send_with_nonce` maps each `OffchainRequestRejected` to an outcome (`outcome_of`; an `OffchainTopUpFailed`, mech-client's auto top-up failing on our side, is `not_accepted` and frees the nonce) and retries a 503 on the same nonce, and a refusal carries what a top-up deposited before the mech refused anyway (`NonceRefused.deposited`, which `mech.py` audits as `mech_deposit`); `exclusive` is the on-chain path's wait for an empty queue. `reserve` writes the slot as unknown and saves before the POST (a save that fails refuses the request instead), and its `finally` keeps a nonce held when a send raises mid-flight; a file it cannot read or write refuses requests (`mech-queue-unreadable`, `mech-queue-unwritable`). `marketplace_contract` (in `mech_allowances.py`) is the one place that reaches mech-client's private `_get_marketplace_contract`. `offchain_send` tells a failure before mech-client's pre-sign hook (nothing reached the mech: `MechNotSent`, the nonce freed) from one after it (held as unknown, and raised as `NonceAnswerUnknown`, rule `mech-answer-unknown`, with the hook's nonce, as a 5xx answer is, so `mech.py` keeps the signed request's id pending). A slot's settle clock starts at its delivery (`delivered`, fed by `mech.py`) or at the end of the 300 s response timeout; the settle timeout and gap retries come from `AppConfig`. On both paths the lock covers only `ACK_WAIT_SECONDS` (in `mech.py`) of the delivery wait; `MechService._resume_watch` waits out the rest after it is released and never loses a paid-for payload to a failed read (`watch_errors`), nor a delivery's url (`delivery_urls`).
- `connect/mech_chat.py` — the chat-tool contract: `is_chat_prompt` and `chat_report` (completion and usage from a delivery, unrequested tool calls as fenced bash blocks).
- `connect/mech_signer.py` — `MechSigner`, mech-client's `Signer` protocol over our guarded signer: every transaction goes through `Signer.send(..., intent=SERVER_BUILT)` (the mech flow builds its own calls, bounded by `max_payment` and its allowances) and every digest through `Signer.sign_digest()`. Split out of `mech.py` for pylint's line limit; `from connect.mech import MechSigner` still resolves.
- `connect/mech_allowances.py` — the single-use grants that flow registers with the guard before it signs or spends: the safe's ERC-1271 wrap of a request id it derived locally (trusting no RPC for anything signed; since mech-client 0.25.0 the derivation runs in `OffchainDigests.on_request_id`, mech-client's pre-sign hook, against the nonce Connect allocated, and a reported id that differs is refused before signing) and the one capped safe→tracker deposit a 402 top-up would send. Split out of `mech.py`, which was over pylint's 1000-line limit; the seam is real, and `MechService` no longer holds the guard at all — this is its whole relationship with it.
- `connect/mech_budget.py` — the default `max_payment` per mech-client `PaymentType` (0.1 of the payment asset) and the token each type is paid in on a chain, which `mech_tools` reports as `payment_token`. Split out of `mech.py` for the same line limit.
- Mech report: `tools()` for the single-mech report, and `_prepare` before any allowance is armed (so a failure spends nothing), call mech-client's `ToolManager.mech_report_or_terms(mech, document)` directly, inside `listing_mechs()` so its indexer reads do not log false RPC mismatch warnings after a request on another chain. There is no deadline of connect's own: a slow proof host stalls only the report on the mech being paid, and the request's `timeout` does not bound the other steps before payment either. Everything is mech-client's: with a readable document and record the report is `ToolManager.mech_report`, the terms keys (`valory_operated`, `terms` for a Valory mech, `identification_note` when the DNS check could not complete, the operator's validated `terms_url`) plus `operator` (`domain`, `url`, `domain_verified`, `verification_note`, `claimed_name`, `name_note`), `benchmarks` (tool to link) and `benchmark_note`, `delivery` (counters, `since`, `age_days`, `note`) and `payment` (`type`, `note`); an unreadable manifest or record gives the terms plus `report_note`. The on-chain flow never reads the document and calls `terms_report(mech, None)`. The domain is the operator's identity and the name only its claim; the skill tells the agent to name the domain, and that a missing `operator` means the operator is unknown unless `valory_operated`. The report fields explain themselves through their notes, so the skill and tool descriptions name them and add only what the report cannot say. Each report is its own check: a DNS lookup, an indexer read, an agent-id lookup and a proof fetch, none memoised upstream, and mech-client 0.24.0 runs one more DNS check inside `send_request`; two reports in one flow can disagree after a blip, and `mech_request`'s governs the request it sent. `route_mech_client_logs` in `__main__.py` sends mech-client's logger (stdout-only, propagation off, by its own setup) through the root handlers, so its warnings reach `log.txt`. Do not restate or recompute any of mech-client's rules here. `test_tools_use_mech_client_s_real_report` and the two fallback guards run the pinned mech-client's real implementation past a faked resolver, indexer, agent-id lookup and proof fetch, so a pin bump that changes its shape fails there.
- `connect/mech_rpc.py` — mech-client reads the RPC from the process-global `MECHX_CHAIN_RPC` (valory-xyz/mech-client#247), so `RPC_LOCK` serialises the places that must set it: building a chain's service, and just before a request is sent, because an auto-deposit rebuilds a mech-client service mid-send. Listing never sets it or takes the lock — a subgraph query can run for minutes — and only reads it for a chain-id check, so `listing_mechs()` drops the stale-RPC warning that check raises, for that thread only.
- `connect/mech_types.py` — the errors and shapes `mech.py`, `mech_allowances.py` and `mech_nonces.py` share, in none of them so they do not import in a circle: `MechError`, and `MechNotSent` for a failure before anything reached the mech (`request()` then frees the caller's `request_id`), `MechAnswerUnknown` for a mech whose answer was lost after signing (its `pending_request_ids` registered for `mech_result`, derived in `MechService._send` from the nonce `NonceAnswerUnknown` carries), and `PendingDelivery`. `from connect.mech import MechError` still resolves.
- `connect/mech_metadata.py` — a mech's published service metadata, which only `mech.py` reads: `read_service_metadata` (the one fetch of it, keeping a failure's cause), `MetadataRead` and `offchain_blocker` (why the off-chain flow is ruled out). Split out of `mech.py` for its line limit; it imports mech-client, which `mech_types.py` need not.
- `connect/idempotency.py` — at-most-once execution keyed by caller-chosen request ids, for actions paid for before they are answered; `mech.py` is the only user, and `signer.py` keeps its own simpler cache mapping ids to tx hashes. Its entries hold a whole report plus a stamp of what was asked, because a replay has to resume a watch rather than repeat a value, and a reused id must not answer a different question.
- `connect/config.py` — the only module that reads env vars *as configuration* (`CONNECTION_*`, injected by Pearl from the service template; `MECH_SETTLE_TIMEOUT` and `MECH_GAP_RETRIES` tune the nonce allocator); `workspace.harness_env()` touches the environment only to scrub it on the way out, and `workspace.terminal_launches()` reads `$TERMINAL` only to pick the operator's terminal.
- `connect/activity.py` — audit trail of every signer action + `agent_performance.json` (Pearl SDK contract file), including the `activity_goal` block from `RunGoal`. The agent top-up is audited only under its own kinds (`send(..., audit=False)`), which `HOUSEKEEPING_KINDS` keeps out of the `transactions` metric and `last_activity` (README, "Agent top-up"). `activity_goal.target` is the one field the session may write, and the user's minutes per run live there (README, "Run window"): every write reads it back first under `_lock`, adopts a whole number >= 0 (audited as `minutes_per_run_changed`, or as `minutes_per_run_restored` on the first read of a process, which may hold the value from before a restart or an edit made while Connect was stopped) and puts the current target back over anything else, including a file it cannot parse at all, with a warning. Window state is per-process by design; only the target persists, and once stored the file's value wins over `CONNECTION_CONFIGS_CONFIG_MINUTES_PER_RUN`. The brief's "Minutes per run" section is the session's only instruction for changing it — no MCP tool, route or setting exists for it.
- `connect/run_goal.py` — `RunGoal`, Connect's activity goal: one run window per process, opened at start and never rolled over, with a target of `target` minutes (default `CONNECTION_CONFIGS_CONFIG_MINUTES_PER_RUN`, 15). `check_target` is the one validation of a target (whole number >= 0, not a bool), shared by the env var parser, the read-back in `activity.py` and `RunGoal` itself. `is_met` is `progress >= target`, so it stays true for the rest of the process unless the target is raised above the progress made; a target of 0 is met at once. `last_met_at` is stamped once, the first time the goal is seen met. Connect never stops itself; Pearl's Auto-run hands over on `is_met`.
- `connect/chains.py` — the one list of supported chains (`SUPPORTED_CHAINS`: chain id, native symbol, and whether a mech marketplace or the facilitator is there), which `wallet_overview` merges into each chain's entry. `marketplace` is read from the pinned mech-client's own `configs/mechs.json` (a non-zero `mech_marketplace_contract`), through `MECH_CLIENT_CHAIN_NAMES` where mech-client names a chain differently (`arbitrum_one` is its `arbitrum`); `facilitator` is Connect's own table and starts empty. `NATIVE_ERC20_FACES` names the ERC-20 contract that is also a chain's native coin (Celo's), which `intent.py` sums with the synthetic native logs.
- `connect/wallet.py` — balance queries shared by `/funds-status`, `/wallet`, and the `wallet_info` MCP tool. It also holds Connect's own copy of funds-manager's agent top-up rule (`plan_agent_topup`, read by `agent_topup` and `funds_status`; README, "Agent top-up").

Server (`connect/server/`):

- `app.py` — FastAPI application factory; also serves the bundled UI from `connect/assets/ui` (read into memory at boot). Its lifespan runs `refresh_performance`, which rewrites `agent_performance.json` every `PERFORMANCE_REFRESH_SECONDS` (15) off the event loop, so `progress` and `is_met` stay current and a session's edit of `activity_goal.target` takes effect with nothing else happening; a failed write is logged and never ends the job, which is cancelled on shutdown. Beside it runs `top_up_agent`, the agent top-up (README, "Agent top-up"), which keeps the chains whose last top-up succeeded in `app.state.topped_up` for `/funds-status`.
- `auth.py` — bearer-token auth with scoped grants (README, "Scoped tokens"), Origin/Host validation, auth-failure rate limiting. `GrantStore` holds the workspace token's `read`+`mech`+`tx` grant, the root every narrower token `POST /tokens` mints descends from; `authorize` checks a token's scope, expiry and caps per action (`ACTION_SCOPES`), holds declared approvals to the caps, and refuses `sign_message` to a value-capped token. `TokenGrant` is a frozen `StrictBody`, its cap keys normalised to the gate's balance keys at mint; the store keeps and hands out copies, so no caller widens a live grant in place. Both surfaces stamp the token on the request (`AUTH_TOKEN` in the request state; `request_token` reads it back); both then ask `GrantStore.intent_for(token, intent)`, which wraps a value-capped token's intent in `intent.Capped` and treats a missing or unknown token as capped. Declared approvals draw on the session budget like spend, an ERC-20 approval of Permit2 included (Permit2 also honours grants made before this token, which the gate cannot see), except an approval whose spender is a Uniswap Universal Router `KNOWN_CONTRACTS` ships on the call's `chain` (the router pulls only from its own caller, so only the safe's own swaps, which draw as spend, can use it); amounts are parsed by `intent.parse_amount`, the gate's own rule. A retry of a `request_id` is drawn only past what the same token already drew for it (`GrantStore._drawn`, keyed by token, action and id), and only while the signer holds the id, sent or in flight (`Signer.holds_request`, injected as the required `GrantStore(held=...)`): then it sends nothing new. Because the hold can end between authorizing and sending, `authorize` returns whether it spared a draw, and that call reaches the signer `replay_only` (`Signer._send_guarded`: answered from the id's result, or refused, never sent fresh); the HTTP routes pass it from `authorize_route`, the MCP mount stamps the spared (tool, id) pairs under `REPLAYS` for the tools to read (`is_replay`). `RequireAuth` and `AuthMiddleware` take the `GrantStore` itself. Every surface words a refusal as `GrantRefused.message` (`rule '<rule>': <detail>`, the prefix the shipped client reads); HTTP routes call `authorize_route` with their body, and `refused_route` audits and answers a refusal for them; the MCP mount's `AuthMiddleware` reads the JSON-RPC body, authorizes each `tools/call` and replays the body to the MCP app. The localhost bind is *not* trusted: any browser page can hit localhost, so every fund-moving or guardrail-changing route needs the bearer token (or the keystore password for protected settings). Only `POST /session` and the harness half of `PATCH /settings` are origin-gated without a token — deliberately, because they can't move funds.
- `pearl_routes.py` — Pearl SDK contracts (`/healthcheck`, `/funds-status`); `is_healthy` flips true only once the workspace is populated.
- `signer_routes.py` / `settings_routes.py` — HTTP signing surface and settings. `/safe-transaction` takes `target` (the safe's call), `/sign-and-send` takes `to` (the EOA's).
- `strict.py` — unknown parameters are refused by name on both surfaces: `StrictBody` for HTTP bodies, and `make_tools_strict` swaps each MCP tool's argument model (through FastMCP's private `_tool_manager`: it has no public hook) for one that forbids extras, so a mistyped name is an error naming the expected ones (with a `to`/`target` hint) instead of a silently dropped field.
- `mcp_tools.py` — MCP (streamable HTTP) at `/mcp`; thin adapters over signer/wallet. `preflight_transaction` first asks `GrantStore.authorize(..., draw=False)` for the send it stands for, so a token's cap refusal is answered (and audited as `checked`) without drawing on its budget. The MCP SDK calls sync tools inline on the event loop, so blocking bodies are pushed to worker threads.

Other trees:

- `connect/assets/skills/` — skills bundled into the agent workspace (`pearl-connect`, `connect-polymarket`, `connect-stocktokens`, `connect-pons`). These run in the agent's environment, not the server process: excluded from coverage and (for connect-polymarket) mypy; tested by `tests/test_connect_polymarket_skill.py`, `tests/test_connect_polymarket_trade_guard.py`, `tests/test_connect_stocktokens_skill.py` and `tests/test_connect_pons_{core,discovery,trade,launch}.py`; the shared library by `tests/test_connect_lib.py`. `connect-stocktokens` trades Robinhood Chain Stock Tokens by quoting every Uniswap v2/v3/v4 pool it can discover from the factories and encoding the Universal Router call itself — no routing API, no API key. The chain- and venue-generic half lives in `connect/assets/lib/` (`evm.py`, `uniswap.py` with addresses and CREATE2 init-code hashes in `DEPLOYMENTS` keyed by chain id, `permit.py`, `router.py` — the approvals, optional signed permit, and verified `execute()` call for one swap, with native ETH paid as value on v4 — `ipfs.py` (the gateway image check), `web.py`, `state.py` and `cli.py` (HTTP GETs, API field checks and page text; JSON state files and ask-once operator answers; printed output and input byte limits), and `bootstrap_env.sh`, the workspace-venv builder the trading skills wrap with their own package list), which `workspace.py` installs as `lib/` next to the skills under `.claude/` and `.agents/`; the skill keeps only what is Robinhood — the registry, the reference price and the multiplier that reconciles them, read from the token contract's `uiMultiplier()` at trade time rather than from the REST registry. Skill modules reach the library through `sys.path`, the same way they reach `pearl-connect`. Its swap inputs carry an undocumented `uint256[] minHopPriceX36` the deployed router expects; without it the call reverts with `SliceOutOfBounds()`. Parity against Uniswap's own Trading API is pinned by golden calldata fixtures in the tests. Hook-less pools are the only v4 pools enumerable without an indexer, so `swap.py` also checks its best quote against Robinhood's own REST price and refuses past 150 bps — the floor alone cannot catch a dislocated pool, because the floor is derived from the same quote. A buy is two safe calls, not three: the router's Permit2 allowance rides inside the swap as an ERC-1271 permit the safe signs (`permit.py` wraps the Permit2 digest in the safe's own `SafeMessage`, which is what its fallback handler verifies), and `--separate-approvals` falls back to an on-chain approval when digest signing is refused. Both the swap calldata and the signed permit are decoded and checked against the plan before either reaches the signer, each call is confirmed before the next is sent, and a quote only scores zero when the pool itself reverts — a timeout, an empty read or a missing deployment address propagates, because an empty market and a broken endpoint must not look alike. The slippage floor is a fraction of the quote, never of Robinhood's reference: the reference drives the two-sided gap refusal instead, so a reference that breaks downward cannot quietly remove the protection. MultiSend is not an option for batching — the guard floor refuses delegatecall. `connect-pons` trades and launches on the Pons memecoin launchpad (V1: locked v3 pools vs WETH; V2: a bonding curve that graduates into a v4 pool behind Pons's fee hook, which `uniswap.discover` cannot see, so `pons.launch_record` builds the PoolKey from the factory's record). Pons's website API is used only to find tokens: every result is re-read from the factories before it is shown, and an unreachable or reshaped API falls back to a bounded launch-event scan, announced rather than silent. V2 is unaudited, so the first V2 trade or launch needs the operator's once-recorded answer (`pons.audit.json`), and every V2 plan re-reads the docs' audit status live. Curve quotes reproduce the deployed curve's maths (the published source lags the deployment — it has no snipe tax — so that part follows the docs).
- `packages/` — Olas SDK package tree (agent blueprint + service package defining the env-var overrides). After changing: `autonomy packages sync && autonomy packages lock && autonomy push-all`.
- `packaging/pyinstaller.spec` — release binaries are built by `.github/workflows/release.yml` on a GitHub release.

## Dependency quirks

- `open-aea-ledger-ethereum` is pinned direct, though mech-client already resolved it at the same version. Importing mech-client already loads the `aea` core and this plugin, so the pin costs no modules in the process or the bundle; it only stops a transitive bump from moving it. The mypy env silences the import rather than installing it: the package ships `py.typed`, but installing it drags in a real `web3` too, which un-silences `[mypy-web3.*]` across the whole tree.
- `mech-client` is pinned to `0.25.0`, the first release with valory-xyz/mech-client#272, which adds caller-owned off-chain nonces (`send_request(..., nonces=, on_request_id=)`), the result's `nonces` and `OffchainRequestRejected`, which the nonce allocator relies on (README, "Mech requests"). Before it, `0.24.0` was the first release with `ToolManager.mech_report` and `mech_report_or_terms` (operator domain verification, benchmark links, delivery record, payment method, and the fallback to the terms). `0.23.3` was the first with `ToolManager.terms_report` and DNS identification of Valory mechs. `0.23.0` was the first that lists Robinhood Chain's mechs (its marketplace indexer is a squid, which 0.22.x could not query). `0.22.0` was the first carrying the `deliveries`/`DeliveryResult` shape `connect/mech.py` reads. `mech_request`'s default `max_payment` is 0.1 of the mech's payment asset, keyed by mech-client's `PaymentType` (`DEFAULT_MAX_PAYMENT` in `connect/mech_budget.py`), so a payment type added upstream is refused until it gets a default.
- `[tool.uv] override-dependencies` pins fastapi past mech-client's transitive `fastapi<0.118` pin (operate paths in mech-client never run here). This is why the pylint/test tox envs use `uv sync` in `commands_pre` instead of a normal package install — pip can't honor the override.
- pytest runs with `-p no:anchorpy` (a transitive plugin whose own deps aren't installed).
